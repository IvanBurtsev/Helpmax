# Аудит сайта sales.femida-ai.ru

Дата: 19.11.2026. Аудит выполнен из авторизованной сессии, без изменения данных.

## Что это за система

Next.js (App Router), вход по паролю: `POST /api/sales-auth/login`, дальше — cookie-сессия.
Внутренний сервис отдела продаж, не клиентский портал.

Разделы:

| Маршрут | Название | Назначение |
|---|---|---|
| `/calc` | Калькулятор стоимости | расчёт цены банкротства, `GET /api/price-list` |
| `/reghelp` | Помощник по регламентам | RAG-чат по базе правил, `POST /api/rules-chat` |
| `/conversion` | Отчёт по конверсии | аналитика |
| `/target-leads` | Отчёт по целевым заявкам | аналитика |
| `/average-check` | Отчёт по среднему чеку | аналитика |
| `/calls` | Расшифровка звонков | транскрипты |
| `/contracts` | Генератор договоров | документы |
| `/documents` | Формирование списка документов | **ядро для бота** |
| `/fssp` | Проверка ФССП | проверка должников |

## Главная находка: `/documents`

Страница уже делает ровно то, что нужно боту: по анкете клиента формирует
список документов, позволяет править вручную и скачать `.doc`.

### Каталог

- **46 документов**, 9 источников: Госуслуги, Мой налог, ЛК налогоплательщика,
  Сбербанк, Кредитные организации, Ипотека, Документы ИП, Данные для исключения
  аренды, Прочие документы.
- **13 условий**: `pension`, `social`, `selfEmployed`, `officialWork`,
  `realEstateDeal`, `securedCredit`, `mortgage`, `creditCards`, `ip`,
  `otherDebts`, `children`, `spouse`, `divorce`.
- Типы правил:

| Правило | Кол-во | Смысл |
|---|---|---|
| `always` | 13 | нужно всегда |
| `manual` | 9 | решает менеджер |
| `spouse` | 6 | есть супруг(а) |
| `mortgage` | 4 | есть ипотека |
| `selfEmployed` | 2 | самозанятый |
| `ip` | 2 | заполнен анализ ИП |
| `pension` | 2 | пенсия |
| остальные 8 | по 1 | `social`, `officialWork`, `realEstateDeal`, `securedCredit`, `creditCards`, `otherDebts`, `children`, `divorce` |

Итого 46: 13 + 9 + 6 + 4 + 2 + 2 + 2 + 8 = 46.

Выгрузка каталога: `content/catalog.json` (id, source, name, note, rule, commentable).
В исходной выгрузке поле `commentable` есть только у 7 из 46 документов; в
`content/catalog.json` оно нормализовано: отсутствующее значение = `false`.
Для бота это менеджерская метка, на выдачу чек-листа она не влияет.

### API разбора анкеты

```
POST /api/documents-conditions
Content-Type: application/json

{ "text": "текст анкеты клиента" }
```

Ответ (проверено):

```json
{
  "conditions": {
    "pension": false, "social": false, "selfEmployed": true,
    "officialWork": false, "realEstateDeal": false, "securedCredit": true,
    "mortgage": true, "creditCards": false, "ip": false,
    "otherDebts": false, "children": false, "spouse": true, "divorce": false
  },
  "reasons": { "spouse": "клиент в браке", "mortgage": "есть ипотека" },
  "sources": { "spouse": "model" },
  "creditors": [],
  "creditorsSource": "fallback",
  "realEstateDeals": []
}
```

Разбор делает модель: `sources[...] = "model" | "fallback"`, есть `reasons`.
То есть это не жёсткий парсер, а LLM-извлечение признаков из текста.

### Применение правил (на клиенте)

```js
selected = rule === "always" ? true
         : rule === "manual" ? false
         : conditions[rule] === true
```

Документы с `manual` менеджер включает руками. Экспорт — `.doc` (HTML + BOM),
генерируется в браузере, серверного PDF нет.

## `/reghelp` — база знаний

```
POST /api/rules-chat
{ "question": "..." }
→ { "answer": "...", "matchedRules": ["...", "..."] }
```

Проверено: отвечает только по найденным регламентам, перечисляет использованные
правила. Это готовый источник пошаговых инструкций «что проверить / что запросить».

## Что это значит для бота

1. **Не писать чек-лист заново.** Каталог и правила уже есть. Бот — клиентский
   интерфейс к существующему движку.
2. **Структурированные ответы бота → 13 условий напрямую.** Бот задаёт вопросы
   кнопками, поэтому LLM для разбора не нужен: маппинг «ответ → условие»
   детерминированный и тестируемый.
3. **Свободный текст / готовая анкета → `/api/documents-conditions`.** Как на сайте,
   чтобы не расходиться в трактовке.
4. **Пояснения «где получить» → `/api/rules-chat` + `note`/`source` каталога.**
   Не выдумывать инструкции, а брать из регламентов.
5. **Единый источник правды.** `content/catalog.json` должен генерироваться из
   одного места (сейчас он зашит в JS-бандл).

## Что нужно доработать на стороне сайта

| Задача | Зачем |
|---|---|
| Service-to-service авторизация для `/api/documents-conditions` и `/api/rules-chat` | бот не может жить на пароле продаж; нужен отдельный токен |
| Экспорт каталога в JSON по API | не парсить бандл при каждом релизе |
| Серверный экспорт PDF/DOC | одинаковый документ в боте и на сайте |
| Разделение «клиентские» и «менеджерские» документы | 9 `manual` нельзя показывать клиенту как обязательные |
| Версия каталога и регламентов | сессия бота должна ссылаться на версию |

## Риски и наблюдения

- Вся логика заточена под **банкротство физлиц**. Для других сценариев нужен
  отдельный каталог и свой набор условий.
- 13 документов «нужно всегда» — для клиента это тяжёлый список. В боте нужен
  прогрессивный вывод: сначала 5–7 ключевых, остальное «после консультации».
- 9 документов «решает менеджер» — в клиентском боте либо скрыть, либо помечать
  «уточнит юрист», иначе человек запутается.
- У части документов нет пошаговой инструкции, только `note`. Инструкции лежат
  в регламентах — их и нужно подтягивать.
- Авторизация одним паролем, без ролей и без аудита действий. Для бота это
  неприемлемо: нужен отдельный сервисный доступ.
- Пароль от сайта нельзя использовать в боте и нельзя хранить в его конфиге.

## Вывод

На сайте уже есть 70–80% нужной логики. Задача бота — не строить движок, а дать
клиенту удобный вход и вынести правила в общий слой.

Сроки зависят от объёма:

- **прототип на тестовых данных** (один сценарий, без админки и PDF) — 1–2 недели;
- **MVP по `docs/product.md`** (сценарий, PDF/ссылка, лимиты, логи, админка) — 4–6 недель;
- полный v1 с CRM и напоминаниями — отдельный план после ответов бизнеса.

Не путать прототип и MVP: в письме руководителю обещать «MVP за неделю» нельзя.
