- Каталог: **46 документов**, 9 источников.
- **13 условий**: `pension`, `social`, `selfEmployed`, `officialWork`, `realEstateDeal`,

  Итого 46.
- Применение: `always → true`, `manual → false`, иначе `conditions[rule] === true`.
- `manual` — менеджерская метка. Клиенту не показываем как обязательное,
  максимум «уточнит юрист».

### API (проверены вживую)

```
POST /api/documents-conditions
{ "text": "анкета клиента" }
→ {
    "conditions": { "spouse": true, "mortgage": true, ... },   // 13 boolean
    "reasons":    { "spouse": "клиент в браке", ... },
    "sources":    { "spouse": "model" | "fallback", ... },
    "creditors": [],
    "creditorsSource": "fallback",
    "realEstateDeals": []
  }
```

```
POST /api/rules-chat
{ "question": "..." }
→ { "answer": "...", "matchedRules": ["...", "..."] }
```

`GET /api/price-list` — цены (не проверялся детально).

**Важно:** оба POST закрыты cookie-сессией продаж. Для бота нужен сервисный токен
или внутренний эндпоинт. Использовать пароль продаж в боте запрещено.

## 3. Принятые решения (не пересматривать без причины)

1. **Детерминированный движок.** Ответы бота → 13 условий напрямую. LLM не решает,
   какие документы нужны. Сценарий **не дублирует** перечень документов: он
   описывает `conditions`, а чек-лист собирается из `catalog.json` по `rule`.
   Явный список `documents` — только для сценария, которого нет на сайте.
2. **LLM только там, где она уже есть на сайте:** разбор свободного текста
   (`/api/documents-conditions`) и ответы по регламентам (`/api/rules-chat`),
   с валидацией и fallback.
3. **Один backend на бота и сайт.** Сайт и бот — клиенты одного API и одной БД.
4. **Webhook → очередь → воркеры.** 200 отдаётся сразу, работа асинхронная.
5. **Postgres — истина, Redis — кэш/очередь/лимиты.**
6. **Контент версионируется.** Сессия идёт по версии, с которой началась.
7. **`manual`-документы не показываем клиенту как обязательные** — помечаем
   «уточнит юрист».
8. **13 `always` — слишком много для клиента.** Выводим прогрессивно: сначала 5–7
   ключевых, остальное — «после консультации».
9. **Свой data-driven движок, а не `ScenarioEngine` из SDK.** У официального SDK
   есть `ScenarioEngine`/`defineScenario`, но он код-driven (шаги — функции TS) и
   хранит состояние в сессии (по умолчанию в памяти). Нам нужен YAML без деплоя
   кода, версионирование и мультиреплика. Из SDK берём транспорт (`Api`,
   `Keyboard`, `fmt`), а не диалоговый граф.

## 5. Факты по API MAX (проверено по dev.max.ru 19.11.2026)

- База: `https://platform-api2.max.ru` (не `platform-api.max.ru`).
- Авторизация: заголовок `Authorization: <access_token>`.
  **Query-параметр больше не поддерживается.**
- Лимит: **30 rps**; держать 25.
- Production — **только webhook**. Long Polling — dev, ограничен.
- Webhook: HTTPS, **порт 443**, доверенный сертификат (в т.ч. Минцифры),
  полная цепочка; HTTP и самоподписанные запрещены с 25.05.2026.
- Ответ endpoint: **200 за 30 секунд**, иначе ретраи (10 попыток, до 8 часов,
  потом отписка).
- Секрет: `POST /subscriptions` с `secret` (5–256 символов `[A-Za-z0-9_-]`) →
  заголовок `X-Max-Bot-Api-Secret` на каждом запросе. Сравнивать через
  `timingSafeEqual`, не через `===`.
- Deep link: `https://max.ru/<botName>?start=<payload>`, payload ≤ 128 символов.
- События: `bot_started`, `message_created`, `message_callback`, `bot_stopped` и др.
- Бот создаётся только после верификации профиля организации/ИП и проходит модерацию.
- В личный диалог бота добавить нельзя — пользователь сам запускает.
- Часть методов (`POST /subscriptions`, `PUT /messages` и др.) возвращает
  **HTTP 200 с `"success": false`** в теле. Проверять и код, и тело.
- Официальная документация: <https://dev.max.ru/docs-api/>,
  webhook: <https://dev.max.ru/docs-api/methods/POST/subscriptions/>,
  диплинки: <https://dev.max.ru/docs/chatbots/bots-coding/prepare/>.
- SDK `@maxhub/max-bot-api` по умолчанию хранит сессии в памяти процесса.
  Для нескольких инстансов нужно внешнее хранилище (Redis/Postgres), иначе
  после рестарта сессии потеряются.
- В SDK есть свой `ScenarioEngine` (`defineScenario`, `transition`) — код-driven.
  Для графа мы его не используем (см. решение 9), но берём `Api`/`Keyboard`/`fmt`.

Обязательно с первого дня:
- проверка `X-Max-Bot-Api-Secret` через `timingSafeEqual`;
- `dedupe_key` (у MAX нет `update_id`):
  - `message_callback` → `chat_id + callback.callback_id + callback.timestamp + user_id + payload`;
  - `message_created` → `chat_id + message.body.mid`;
  - `message_edited` → `message.body.mid + message.timestamp`;
  - служебные → `update_type + chat_id + timestamp`.
  Нельзя брать `mid + payload` для callback: два нажатия одной кнопки схлопнутся
  в один ключ.
- сериализация по `chat_id`;
- ответ 200 сразу после валидации (503 — только при поломке Redis/Postgres);
- проверка `"success": false` в ответах MAX, а не только HTTP-кода;
- логи без ПД (chat_id хэшем), payload не логировать;
- `raw_updates.payload` содержит текст сообщения — retention 30 дней и доступ
  только сервисной роли.
