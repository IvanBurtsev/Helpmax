## 3. Принятые решения (не пересматривать без причины)

1. **Инструкция из данных, а не «промпт».** Список документов и шаги получения
   собираются из каталога и гайдов; LLM не решает, что нужно. Сценарий **не
   дублирует** перечень документов. Опросника нет: показываем весь список сразу.
2. **LLM только для подсказок.** Свободный текст и голос идут помощнику; LLM
   отвечает по конкретному документу, с валидацией и fallback на гайды. Перечень
   документов решает код, а не модель.
3. **Один backend на бота и сайт.** Сайт и бот — клиенты одного API и одной БД.
4. **Webhook → очередь → воркеры.** 200 отдаётся сразу, работа асинхронная.
5. **Postgres — истина, Redis — кэш/очередь/лимиты.**
6. **Контент версионируется.** Сессия идёт по версии, с которой началась.
7. **`manual`-документы не показываем как обязательные** — помечаем «может
   понадобиться». Обязательных и «не нужно» больше нет: список общий.
8. **Показываем все документы сразу.** После «Начать» — полный список (46) без
   вопросов, разбитый на несколько сообщений MAX (лимит длины), не разрывая
   документ между сообщениями.
9. **Свой data-driven движок, а не `ScenarioEngine` из SDK.** У официального SDK
   есть `ScenarioEngine`/`defineScenario`, но он код-driven (шаги — функции TS) и
   хранит состояние в сессии (по умолчанию в памяти). Нам нужен YAML без деплоя
   кода, версионирование и мультиреплика. Из SDK берём транспорт (`Api`,
   `Keyboard`, `fmt`), а не диалоговый граф. Сценарий теперь — один терминальный
   шаг `instruction`.
10. **Помощник не меняет диалог.** Свободный текст, голос и кнопка «Не понятно» —
    это вопрос помощнику: отвечаем коротко и прикладываем кнопку «Начать заново».
    Перечень документов по-прежнему решает код, а не LLM.
11. **LLM заземлена и проверяется на выходе.** Промпт собирается только из
    каталога и гайдов; ссылки вне allowlist вырезаются **в коде** (`sanitizeLinks`),
    длина ограничена. Без `LLM_API_KEY` или при сбое — откат на гайды. DeepSeek —
    текстовая модель, поэтому голос идёт через отдельный STT (`src/stt/`).
12. **Гайды — производный контент.** `content/guides.json` генерируется
    `npm run build:guides` из `source`/`note` каталога, помечен `review_status:
    draft` до ревью юриста. Не выдумываем шаги и ссылки: только официальные
    сервисы и подсказки менеджера.

## 5. Факты по API MAX (проверено по dev.max.ru 19.11.2026)

- База: `https://platform-api2.max.ru` (не `platform-api.max.ru`).
- Авторизация: заголовок `Authorization: <access_token>`.
  **Query-параметр больше не поддерживается.**
- Лимит: **30 rps**; держать 25.
- Production — **только webhook**. Long Polling — dev, ограничен.
- Webhook: HTTPS, **порт 443**, доверенный сертификат (в т.ч. Минцифры),
  полная цепочка; HTTP и самоподписанные запрещены с 25.05.2026.
- Ответ endpoint: **200 за 30 секунд**, иначе ретраи (10 попыток, до 8 часов,
  потом отписка).
- Секрет: `POST /subscriptions` с `secret` (5–256 символов `[A-Za-z0-9_-]`) →
  заголовок `X-Max-Bot-Api-Secret` на каждом запросе. Сравнивать через
  `timingSafeEqual`, не через `===`.
- Deep link: `https://max.ru/<botName>?start=<payload>`, payload ≤ 128 символов.
- События: `bot_started`, `message_created`, `message_callback`, `bot_stopped` и др.
- Бот создаётся только после верификации профиля организации/ИП и проходит модерацию.
- В личный диалог бота добавить нельзя — пользователь сам запускает.
- Часть методов (`POST /subscriptions`, `PUT /messages` и др.) возвращает
  **HTTP 200 с `"success": false`** в теле. Проверять и код, и тело.
- Официальная документация: <https://dev.max.ru/docs-api/>,
  webhook: <https://dev.max.ru/docs-api/methods/POST/subscriptions/>,
  диплинки: <https://dev.max.ru/docs/chatbots/bots-coding/prepare/>.
- SDK `@maxhub/max-bot-api` по умолчанию хранит сессии в памяти процесса.
  Для нескольких инстансов нужно внешнее хранилище (Redis/Postgres), иначе
  после рестарта сессии потеряются.
- В SDK есть свой `ScenarioEngine` (`defineScenario`, `transition`) — код-driven.
  Для графа мы его не используем (см. решение 9), но берём `Api`/`Keyboard`/`fmt`.

## 11. Чего не делать

- Не хранить пароль от сайта в коде, `.env`, логах, тестах, git.
- Не хранить raw deep-link токен в БД: только `sha256(token)`, иначе утечка БД
  даёт возможность переиграть переход.
- Не логировать payload webhook и тексты сообщений: там ПД.
- Не парсить JS-бандл в рантайме — каталог уже выгружен в `content/catalog.json`;
  правильно — получить его по API от команды сайта.
- Не показывать `manual`-документы как обязательные: только «может понадобиться».
- Не использовать LLM для решения, какие документы нужны.
- Не позволять LLM давать ссылки вне allowlist: только официальные сервисы из
  гайдов и сайт продукта. Проверка — в коде (`sanitizeLinks`), а не в промпте.
- Не выдумывать шаги «где получить» и ссылки: гайды собираются из каталога и
  официальных адресов, помечены `review_status: draft` до ревью юриста.
- Не менять данные на `sales.femida-ai.ru` без явного разрешения.
- Не обещать «MVP за неделю»: неделя — это прототип, MVP — 4–6 недель.
- Не просить пользователя платить за подписки из своего кармана.
- Не переписывать существующие docs без причины — они согласованы с пользователем.
  Если правите — фиксируйте причину в `docs/review-2026-11-19.md`.
